# Workflow: Loop Engineering

## 1) Define — ทำให้ “เสร็จ” วัดได้

สร้าง spec จาก `templates/TASK_SPEC.md` โดยเกณฑ์รับงานแต่ละข้อควรตรวจได้ด้วย test, คำสั่ง, ภาพหน้าจอ หรือการสังเกตที่ระบุชัด อย่าเริ่มจากคำสั่งกว้าง ๆ เช่น “ทำให้ดีขึ้น”

## 2) Build — วนแก้โดยมีขอบเขต

| รอบ | สิ่งที่ AI ทำ | ผลลัพธ์ที่ต้องได้ |
| --- | --- | --- |
| 0 | อ่าน spec และสำรวจโค้ด | แผนสั้น ๆ, ไฟล์ที่คาดว่าจะเปลี่ยน, คำสั่งตรวจ |
| 1 | ทำ implementation ขั้นต่ำ | diff พร้อมผลตรวจที่เกี่ยวข้อง |
| 2 | แก้เฉพาะ failure ที่พบ | ผลตรวจใหม่และคำอธิบายสาเหตุ |
| 3 | ตรวจผลกระทบและเก็บงาน | หลักฐานว่าเกณฑ์รับงานครบ หรือ blocker ที่ชัดเจน |

ให้หยุดทันทีเมื่อผ่านทุกเกณฑ์หรือครบ 3 รอบการแก้ไข ห้ามวนเพิ่มเพียงเพราะอยากปรับโค้ดให้สวยขึ้น

## 3) Verify — เชื่อหลักฐาน ไม่เชื่อความมั่นใจ

เลือกคำสั่งตามเทคโนโลยีที่ตรวจพบในโปรเจกต์:

| ประเภท | ตัวอย่างการตรวจ |
| --- | --- |
| JavaScript/TypeScript | test ที่เจาะจง, lint, typecheck, build |
| Python | test ที่เจาะจง, linter/type checker, import หรือ smoke test |
| Backend/API | unit/integration test และเรียก endpoint ในสภาพแวดล้อมปลอดภัย |
| UI | test, build และตรวจหน้าจอหรือภาพที่ render แล้ว |

คำสั่งที่รันไม่ได้ต้องบันทึกไว้พร้อมเหตุผลและทางเลือกที่ทำแทน

บันทึกผลด้วยคำสถานะในตารางของ `templates/TASK_SPEC.md` เท่านั้น ผลที่ได้จากบริการหรือสิทธิ์ที่จำลองขึ้นต้องเขียน `Pass-จำลอง` ไม่ใช่ `Pass` เพราะความเสี่ยงตอนต่อของจริงยังอยู่

ส่วนที่ AI ตรวจเองไม่ได้ (บัญชีจริง, key จริง, สิทธิ์ของ browser/OS, ติดตั้งโปรแกรม, tray/แจ้งเตือนจริง) ให้เขียนเป็นเกณฑ์แยกตั้งแต่ขั้น Define พร้อมขั้นตอนในหัวข้อ "ตรวจโดยคน" — อย่าเสียรอบแก้ไปกับการพยายามตรวจส่วนนี้

## 4) Review — แยกบทบาทผู้สร้างกับผู้ตรวจ

ให้ AI หรือผู้ตรวจอีกครั้งอ่าน diff โดยยังไม่แก้ทันที ตรวจ:

- เกณฑ์รับงานครบและไม่หลุดขอบเขต
- bug, edge case, error handling และ regression
- ความปลอดภัย, secret, สิทธิ์ และข้อมูลส่วนบุคคล
- test ครอบคลุมพฤติกรรมที่เปลี่ยนจริง
- เอกสารและการตั้งค่าถูกต้อง

ข้อพบต้องมีระดับความสำคัญ, ตำแหน่ง, ผลกระทบ และแนวทางแก้ เมื่อแก้แล้วต้องตรวจซ้ำ

## 5) Human gate — คนเป็นผู้ตัดสินใจ

AI เตรียม summary, ผลตรวจ, ความเสี่ยง และข้อความ PR ได้ แต่การ merge/deploy/เปลี่ยนข้อมูลจริงต้องรอคำยืนยันจากคนเสมอ

ทุกข้อ "ตรวจโดยคน" ของทุก spec รวมอยู่ใน [docs/HUMAN_CHECKS.md](HUMAN_CHECKS.md) เป็น checklist เดียว เมื่อคนทดสอบแล้วให้ติ๊กที่นั่น แล้วติ๊กเกณฑ์ใน spec และเปลี่ยน `Status:` เป็น `เสร็จ` เมื่อไม่เหลือข้อค้าง ถ้าทดสอบแล้วไม่ผ่านให้เปิดเป็น spec แก้ไขใหม่

## 6) Scale — งานใหญ่ให้แตกก่อนเข้าลูป

ถ้า Outcome ต้องแก้มากกว่า 1 พื้นที่หลัก หรือเกณฑ์รับงานเกิน ~7 ข้อ ให้แตกเป็นหลาย task spec ย่อยก่อนเข้าลูป แทนที่จะขยายรอบแก้ไขของ spec เดียว:

- ตั้งชื่อ spec ย่อยให้เห็นลำดับ เช่น `2026-08-30-billing-api-1-schema.md`, `2026-08-30-billing-api-2-endpoint.md`
- แต่ละ spec ย่อยผ่าน Human gate เป็นอิสระ ก่อนเริ่ม spec ถัดไปที่ต่อยอดจากมัน
- spec หลัก (epic) เก็บไว้เป็นตัวเชื่อมลิงก์ไปยัง spec ย่อยเท่านั้น ไม่ต้องมี acceptance criteria ของตัวเอง

## 7) Retro — ปรับกติกาจากของจริง

การบันทึก RETRO เป็นขั้นตอนบังคับก่อนจบ spec ไม่ใช่ทางเลือก — เพิ่มแถวใน [docs/RETRO.md](RETRO.md) เมื่อเกิดอย่างใดอย่างหนึ่ง:

- ครบ 3 รอบแก้ (แม้สุดท้ายจะผ่าน)
- ติด blocker หรือต้องรอคนทำบางอย่างก่อนไปต่อ
- มีข้อ "ตรวจโดยคน"
- `Not run` ด้วยเหตุผลเดิมซ้ำจาก spec ก่อน — ครบ 3 spec เมื่อไหร่ให้เสนอเปิด spec แก้ต้นเหตุ

ข้อเสนอปรับกติกาในคอลัมน์สุดท้ายต้องมีผลลัพธ์อย่างใดอย่างหนึ่งภายใน spec ถัดไป: นำไปใช้แล้ว (ระบุไฟล์ที่แก้) หรือตัดสินใจไม่ทำ (ระบุเหตุผล) — ข้อเสนอที่ค้างเป็น "ยังไม่ปรับ" คือสัญญาณว่ากระบวนการกำลังไม่เรียนรู้

## 8) ตรวจกติกาด้วยเครื่อง

`node scripts/check-docs.mjs` ตรวจกติกาส่วนที่ตรวจด้วยเครื่องได้ และ CI รันคำสั่งเดียวกันทุก push/PR ไป main (job `docs` ใน `.github/workflows/verify.yml`) — รันให้ผ่านก่อนจบทุก spec

| กติกา | ตรวจว่า |
| --- | --- |
| ลิงก์ | ลิงก์ relative ในไฟล์ markdown ชี้ไปไฟล์ที่มีจริง ตัวพิมพ์ตรง (CI เป็น Linux) และไม่ออกนอก repo |
| รูปแบบ spec | spec ตั้งแต่ 2026-10-29 มี `Status:` ที่ใช้ได้ และคำสถานะใน Validation plan อยู่ในชุดของ `templates/TASK_SPEC.md` |
| Status กับเกณฑ์ | `เสร็จ` ไม่มีเกณฑ์ค้าง; `เสร็จ–รอคนตรวจ`, `Pass-จำลอง` หรือ `ตรวจโดยคน` ต้องมีขั้นตอนในหัวข้อ "ตรวจโดยคน" |
| HUMAN_CHECKS | เกณฑ์ที่ยังไม่ติ๊กของ spec ที่จบแล้ว ตรงกับข้อค้างใน [HUMAN_CHECKS.md](HUMAN_CHECKS.md) ทั้งสองทาง — จับคู่ด้วยรหัสเกณฑ์ (`AC3`) และลิงก์ไปที่ spec |
| RETRO | spec ที่ครบ 3 รอบ ติด blocker หรือมีข้อตรวจโดยคน มีแถวใน [RETRO.md](RETRO.md) ที่ลิงก์มาที่ spec |

spec ที่เขียนก่อน 2026-10-29 เป็นบันทึกเดิม จึงไม่ถูกบังคับเรื่อง `Status:` และคำสถานะ แต่ยังถูกตรวจลิงก์, HUMAN_CHECKS และ RETRO

ส่วนที่ต้องใช้วิจารณญาณ — เหตุผล `Not run` ที่ซ้ำ, ข้อเสนอใน RETRO ที่ค้าง, หลักฐานพอหรือไม่ — เครื่องตรวจไม่ได้ ยังเป็นหน้าที่ของผู้ทำงานและผู้ review
